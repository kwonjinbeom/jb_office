# 글쓰기 루틴

안내문의 날짜에, 안내문 '오늘의 자료 › 오늘 쓸 분류'에 적힌 분류와 편수만큼 원고를 쓴다. 기본은 하루 11편이다
(광고 수익 하위에서 무작위 6 · 판매 수익 하위에서 무작위 3 · IT/AI 에서 2). 사용자가 일일루틴 화면에서 분류·편수를 고르면 그것을 따른다.
티스토리·네이버 구분은 없다. 글은 한 분류 트리로 쓰고, 사이트·플랫폼에 맞추는 일은 마지막 단계(사이트별 템플릿의 변환)에서 한다.
리스트의 '실행'·'전체 실행'과 '추가 실행'(더 쓰고 싶을 때)이 이 md 를 똑같이 따른다.
안내문에 '오늘 쓸 분류' 대신 '이번에 할 것 (추가 실행)'이 있으면 그만큼만 쓴다. 사용자 코멘트면 편수·주제·분류를 코멘트대로 하고, 분류가 없으면 '글 분류 전체'에서 맞는 중분류를 고른다.

## 할 일
1. 분류마다 '오늘의 자료 › 사이트·체크'의 운영 사이트 중 컨셉이 가장 맞는 사이트를 하나 정한다. 그 사이트의 체크를 지킨다 (겹침 금지·품질 순서·하루 편수 등).
2. 아래 '조사'를 하고, 분류의 방향·독자의 질문, 아래 '분류별 수요와 잘 쓰인 글'(최신화가 쌓은 것), 오늘 조사로 주제를 정한다. '오늘의 자료 › 이미 있는 글'과 원고 폴더의 기존 원고와 겹치지 않게 한다.
3. 숫자·날짜·정책은 원 출처에서 확인하고, 확인 못 한 것은 쓰지 않거나 제작 정보에 `확인 못 함: <주소>` 로 적는다.
4. 원고마다 맨 위 제작 정보에 아래 두 줄을 꼭 쓴다. 원고 가져오기가 이 줄로 사이트와 분류를 붙인다.
   - `사이트: <운영 화면의 사이트 이름>`
   - `분류: <대분류> > <중분류> > <소분류>` (소분류가 없으면 중분류까지)
5. 저장 위치: 콘텐츠/블로그_카페/포스팅자동화/원고/T번호_짧은이름/원고.md (원고/README.md 형식, 번호는 이어서).
6. 끝나면 main 에 반영한다: `git pull --rebase origin main` 뒤 `git push origin HEAD:main`. main 으로 push 가 막히는 환경이면 지금 브랜치에 push 하고 main 으로 PR 을 만들어 바로 병합한다. 병합까지 해야 서버에 들어간다 (웹훅이 자동 반영).

## 조사 (원고를 쓰기 전에 분류마다 한다)
블로그(네이버·티스토리)를 직접 여는 깊은 조사는 프롬프트 최신화가 PC 에서 하고, 그 결과를 아래 '분류별 수요와 잘 쓰인 글'에 쌓는다. 여기서는 그것을 바탕으로 오늘 것만 확인한다.
1. 오늘 트렌드: WebSearch 로 오늘·이번 주 뉴스와 많이 찾는 말을 찾는다. 분류의 독자 질문과 이어지는 것을 고른다.
2. 사실 확인: 원고에 쓸 숫자·날짜·정책·가격은 공식 출처(기관·제조사·서비스 공지)를 WebSearch·WebFetch 로 확인한다.
3. 안 열리는 곳은 넘어가고 다른 출처로 간다. 블로그 글이 안 열려도 멈추지 않는다.
4. 원고 제작 정보 표에 `| 참고 조사 | 트렌드 출처 · 확인한 공식 출처 · 가져온 점 한 줄 |` 줄을 넣는다.
5. 로그인·댓글·공감·글쓰기는 하지 않는다.

## 분류별 수요와 잘 쓰인 글 (프롬프트 최신화가 쌓는다)

**모든 분류 공통 (2026-10-19 조사에서 반복된 것 — 우리 글의 차별화 공식):**
- 제목: `연도·버전·숫자 + 핵심 질문어(해도 되나·얼마·뭐가 낫나) + 정리어(총정리·BEST·A to Z)` 짜임이 상위 글 공통. 모델명·에러메시지·대회명은 토씨 그대로 박는다. 단 '우리 집/내 기기' 같은 생활어는 상위 글이 잘 안 써서 여기가 빈틈 — 제목·본문에 넣으면 차별화.
- 첫 문단: 서론 없이 **결론·핵심 수치를 먼저** 던지고(날짜·금액·"지금 해라/48시간 대기") 근거는 뒤에. 상위 글일수록 맨 앞에 "결론부터" 한 줄 또는 요약 박스 3~5줄.
- 상위 글 공통으로 빠진 것 = 우리가 더 줄 것: ① 실제 숫자·표(실측·시뮬레이션·비교표) ② '우리 집/내 기기/내 상황'별 개인화 한 줄 ③ 되돌리기·막혔을 때 전화처 같은 실행 디테일 ④ 과장 낚시어 대신 원리 설명. 정보성 글은 구매 링크를 안 거는 경우가 많아, 판매 분류는 '해결→구매' 통로를 우리가 더 자연스럽게 잇는다.
- 조사 한계: `search.naver.com` 블로그 탭은 WebFetch 403 차단, `site:tistory.com` WebSearch 는 US 엔진이라 티스토리가 안 걸린다. 티스토리 본문은 직접 URL 로 WebFetch 하고, 수요는 Google·WebSearch 로 본다.
