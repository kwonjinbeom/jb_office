# pip install 했더니 "externally-managed-environment" 에러, 정답은 상황별로 셋이다 (2026)

<!-- 제휴가 있으면 이 줄에 대가성 문구 -->

새로 설치한 우분투나 맥에서 `pip install requests` 한 줄을 쳤는데 이런 게 뜬다.

```
error: externally-managed-environment

× This environment is externally managed
╰─> To install Python packages system-wide, try apt install
    python3-xyz, where xyz is the package you are trying to
    install.
    ...
note: If you believe this is a mistake, please contact your Python installation or OS distribution provider. You can override this, at the risk of breaking your Python installation or OS, by passing --break-system-packages.
hint: See PEP 668 for the detailed specification.
```

결론부터: **이 에러는 버그가 아니라 "시스템 파이썬에 직접 깔지 말라"는 OS의 요청**이다. 그리고 메시지가 해법을 이미 다 적어 두고 있다.

[사진] 터미널에서 에러가 뜬 화면 캡처 (없으면 이 줄 지움)

## 왜 막는가: PEP 668 한 문단 요약

리눅스 배포판과 Homebrew는 자기 도구를 돌리려고 파이썬과 패키지 일부를 직접 관리한다. 여기에 pip이 같은 자리에 다른 버전을 덮어쓰면 apt나 brew가 깔아 둔 패키지와 충돌해서, 최악엔 OS 도구가 깨진다.

그래서 PEP 668은 규칙을 하나 만들었다. 파이썬 표준 라이브러리 폴더에 **`EXTERNALLY-MANAGED`라는 파일**이 있고 **지금 가상환경 밖**이라면, pip 같은 설치 도구는 설치를 거부한다. `pip install --user`도 같은 이유로 막힌다. pip은 23.0부터 이 파일을 읽는다.

이 파일이 들어간 대표적인 환경은 이렇다.

| 환경 | 상태 |
|---|---|
| Debian 12 이후 | 적용 |
| Ubuntu 23.04 이후 (24.04 포함) | 적용 |
| macOS Homebrew python@3.12 이상 | 적용 |
| Fedora | 적용 제안이 멈춰 있어 보통 안 뜸 |

## 상황별 정답

### 1. 프로젝트에서 쓸 라이브러리라면: 가상환경

가장 흔한 경우다. 프로젝트 폴더마다 독립된 파이썬 환경을 만든다.

```bash
python3 -m venv .venv
source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install requests
```

가상환경 안에서는 마커 검사 조건(가상환경 밖일 것)에 안 걸리니 에러가 사라진다. 우분투에서 `venv` 모듈이 없다고 나오면 `sudo apt install python3-venv`부터.

`uv`를 쓴다면 더 짧다.

```bash
uv venv
uv pip install requests
```

### 2. 명령어로 쓰는 도구라면: pipx 또는 uv tool

`black`, `httpie`, `yt-dlp`처럼 라이브러리가 아니라 **터미널 명령어로 쓰는 도구**는 프로젝트마다 깔 필요가 없다. 도구마다 따로 격리된 환경을 만들어 주는 쪽이 정답이다.

```bash
# pipx
sudo apt install pipx          # macOS: brew install pipx
pipx install black

# 또는 uv
uv tool install black
```

명령어는 전역에서 쓰이는데, 실제 패키지는 각자 격리돼 있어서 시스템 파이썬을 건드리지 않는다.

### 3. 시스템 전체에서 쓰는 걸 OS 방식으로: apt

에러 메시지 첫 줄이 권하는 방법이다. 배포판이 패키징해 둔 버전이면 apt로 깐다.

```bash
sudo apt install python3-requests
```

OS가 버전을 관리해 주니 충돌이 없다. 대신 최신 버전이 아닐 수 있다. 최신이 필요하면 1번으로 간다.

## `--break-system-packages`는 언제 쓰나

메시지 마지막 줄에 있는 그 옵션이다.

```bash
pip install --break-system-packages requests
```

이름 그대로 "시스템 패키지를 깨뜨릴 수 있음을 **알고 쓴다**"는 뜻이다. pip 스스로도 "파이썬이나 OS가 망가질 위험을 감수하고"라고 경고한다. 그나마 써도 되는 건 이런 경우 정도다.

- 버리고 다시 만들 수 있는 **도커 컨테이너** 안. (PEP 668도 단일 앱 컨테이너에선 마커를 빼도 된다고 허용한다.)
- 다른 방법이 정말 안 되는 일회성 실험 환경.

`EXTERNALLY-MANAGED` 파일을 지워 버리는 방법도 검색하면 나오는데, 같은 위험을 영구적으로 켜 두는 것이라 권하지 않는다.

## 한 줄 정리

| 내가 하려는 것 | 정답 |
|---|---|
| 프로젝트 코드에서 import | `python3 -m venv` 또는 `uv venv` |
| 터미널 명령어 도구 | `pipx install` 또는 `uv tool install` |
| OS 전체에서 쓰는 라이브러리 | `apt install python3-xxx` |
| 컨테이너 안 일회성 | `--break-system-packages` (최후 수단) |

에러 메시지가 길어서 놀라지만, 사실 "가상환경 쓰세요"를 길게 말한 것뿐이다. 10월 9일 Python 3.15.0이 나와 새로 설치하는 사람이 많을 텐데, 처음부터 프로젝트마다 `.venv`를 만드는 습관을 들이면 이 에러는 다시 볼 일이 없다.
