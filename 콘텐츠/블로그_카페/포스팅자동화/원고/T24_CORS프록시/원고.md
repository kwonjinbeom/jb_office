# localhost CORS 에러, 프런트 코드 안 건드리고 끝내기 (Vite 프록시 · 2026)

로컬에서 React/Vue를 띄우고 백엔드 API를 부르는 순간 콘솔이 빨개진다.

```
Access to fetch at 'http://localhost:5000/api/users' from origin
'http://localhost:5173' has been blocked by CORS policy:
No 'Access-Control-Allow-Origin' header is present on the requested resource.
```

Postman으로는 되는데 브라우저에서만 막힌다. 익숙한 장면이다. 결론부터: **프런트 `fetch` 주소를 바꾸거나 CORS 확장 프로그램을 까는 건 임시방편이다.** 개발 서버에서는 Vite 프록시 한 줄, 운영에서는 서버 헤더가 정석이다.

![콘솔의 CORS 에러 메시지]

## 왜 막히나 (원인)

CORS는 버그가 아니라 브라우저의 보안 규칙이다. `http://localhost:5173`(프런트)와 `http://localhost:5000`(백엔드)는 포트가 다르므로 브라우저 입장에서 **서로 다른 출처(origin)**다. 다른 출처로 보낸 요청의 응답을 자바스크립트가 읽으려면, 서버가 응답에 `Access-Control-Allow-Origin` 헤더로 "너 읽어도 돼"라고 허락해 줘야 한다. 그 헤더가 없으면 브라우저가 응답을 가로막는다.

핵심 포인트 두 가지.
- **요청은 서버까지 간다.** 서버 로그에는 요청이 찍힌다. 막는 건 브라우저가 응답을 프런트 JS에 넘겨줄 때다. 그래서 Postman/curl은 멀쩡하다(브라우저가 아니니까).
- 그러므로 고칠 수 있는 곳은 **서버 응답 헤더**거나, 아예 **같은 출처로 보이게 만드는 것** 둘 중 하나다.

## 해결 1 — 개발 서버: Vite 프록시 (프런트 코드 안 건드림)

가장 깔끔하다. Vite 개발 서버가 요청을 대신 백엔드로 넘겨주면, 브라우저 눈에는 전부 같은 출처(프런트 서버)로 보여서 CORS 자체가 발생하지 않는다.

`vite.config.js` (또는 `.ts`):

```javascript
import { defineConfig } from 'vite'

export default defineConfig({
  server: {
    proxy: {
      // '/api' 로 시작하는 요청을 백엔드로 전달
      '/api': {
        target: 'http://localhost:5000',
        changeOrigin: true,
      },
    },
  },
})
```

이제 프런트에서는 백엔드 전체 주소 대신 **상대 경로**로 부른다.

```javascript
// 변경 전: fetch('http://localhost:5000/api/users')
fetch('/api/users')   // 변경 후 — 같은 출처라 CORS 없음
```

백엔드 라우트에 `/api` 프리픽스가 없다면 경로를 깎아서 넘긴다.

```javascript
server: {
  proxy: {
    '/api': {
      target: 'http://localhost:8080',
      changeOrigin: true,
      rewrite: (path) => path.replace(/^\/api/, ''), // '/api/users' → '/users'
    },
  },
}
```

- `changeOrigin: true` — 백엔드로 보내는 `Host` 헤더를 target에 맞춰 바꾼다. 가상호스트나 인증 때문에 백엔드가 Host를 따질 때 필요하다. 보통 켜 두면 탈이 없다.
- WebSocket(소켓IO 등)도 프록시하려면 `ws: true`를 준다.

```javascript
'/socket.io': {
  target: 'ws://localhost:5174',
  ws: true,
  rewriteWsOrigin: true,
}
```

Vite의 `server.proxy`는 `http-proxy-3` 기반이라 위 옵션들이 그대로 통한다. 설정을 바꿨으면 **개발 서버를 껐다 켜야** 반영된다.

> 버전 메모: Vite 7(2025-06-24 출시)은 Node.js **20.19+ 또는 22.12+**를 요구하고 ESM-only다. `vite.config`는 위 예시처럼 ESM(`import`/`export default`)으로 쓴다.

## 해결 2 — 서버에서 직접 허락하기 (운영까지 가는 정석)

프록시는 "개발 서버가 떠 있는 동안"만 유효하다. 빌드해서 배포하면 Vite 개발 서버가 없으니 프록시도 없다. 운영에서 다른 도메인의 API를 직접 부른다면 **백엔드가 CORS 헤더를 내려줘야** 한다.

Express라면 `cors` 미들웨어가 표준이다.

```bash
npm install cors
```

```javascript
const express = require('express')
const cors = require('cors')
const app = express()

app.use(cors({
  origin: 'https://your-frontend.com', // 허용할 프런트 출처
  credentials: true,                   // 쿠키/인증 헤더를 쓸 때만
}))
```

Django라면 `django-cors-headers`:

```bash
pip install django-cors-headers
```

```python
# settings.py
INSTALLED_APPS = [
    # ...
    "corsheaders",
]

MIDDLEWARE = [
    "corsheaders.middleware.CorsMiddleware",  # CommonMiddleware 보다 위
    "django.middleware.common.CommonMiddleware",
    # ...
]

CORS_ALLOWED_ORIGINS = [
    "https://your-frontend.com",
]
```

## 하면 안 되는 것

- **`Access-Control-Allow-Origin: *` + 쿠키 인증 동시 사용** — 브라우저가 거부한다. `credentials: true`를 쓰면 origin에 와일드카드 `*`를 못 쓰고 정확한 출처를 지정해야 한다.
- **CORS 비활성화 크롬 확장/`--disable-web-security`** — 내 컴퓨터에서만 "보이게" 만들 뿐, 팀원·운영에서는 그대로 깨진다. 디버깅 말곤 금물.
- **프런트에 백엔드 전체 URL 하드코딩** — 환경마다 주소가 달라져 결국 다시 고친다. 개발은 프록시 + 상대경로, 운영은 서버 헤더로 나눠서 생각하자.

## 정리

| 상황 | 해결 |
|---|---|
| 로컬 개발 (`localhost` 포트만 다름) | Vite `server.proxy` + 프런트는 상대경로 |
| 운영/배포 (프런트·API 도메인 다름) | 백엔드에서 `Access-Control-Allow-Origin` 내려주기 |
| 쿠키/세션 인증 함께 | `credentials: true` + origin 정확히 지정(와일드카드 금지) |

CORS는 "브라우저가 응답을 못 읽게 막는" 규칙이라는 것만 잡으면, 고칠 지점은 **같은 출처로 위장(프록시)** 아니면 **서버가 허락(헤더)** 둘뿐이다.
