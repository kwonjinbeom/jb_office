1. 본인 PC에서 `py install 3.15` 또는 설치 후 `python -X warn_default_encoding` 으로 기존 스크립트를 한 번 돌려 본 결과(경고가 몇 개 떴는지) 한 줄. 실제 경험이 들어가면 개발자 독자 신뢰가 확 오른다.

# 파이썬 3.15 출시, 지금 올려도 될까? 윈도우는 인코딩부터 확인하자

<!-- 제휴가 있으면 이 줄에 대가성 문구 -->

파이썬 3.15가 **2026년 10월 9일** 정식으로 나왔다. 원래 10월 1일 예정이었는데 막판에 lazy import 버그가 나와 RC를 한 번 더(rc3) 돌리고 일주일 늦게 출시됐다. 결론부터 말하면 **새 프로젝트는 바로 써도 되고, 기존 프로젝트는 두 가지만 확인하고 올리자.** 하나는 윈도우의 기본 인코딩이 UTF-8로 바뀐 것, 다른 하나는 이번에 지워진 API다.

기능 소개는 다른 데서도 많이 하니, 여기서는 "올리면 뭐가 깨지고, 뭘 바로 쓸 수 있나" 순서로 정리한다.

## 한눈에 보기

| 구분 | 내용 |
|---|---|
| 출시일 | 2026-10-09 (3.15.0) |
| 지원 기간 | 버그 수정 약 2년(2개월마다), 보안 수정 약 2031년 10월까지 |
| 깨질 수 있는 것 | UTF-8 기본 인코딩(PEP 686), 제거된 API |
| 바로 쓸 만한 것 | lazy import, frozendict, 컴프리헨션 언패킹, Tachyon 프로파일러 |
| 성능 | JIT: x86-64 리눅스 7~8%, 애플 실리콘 맥 11~12% (공식 수치) |

## 1. 윈도우 사용자는 이것부터: 기본 인코딩이 UTF-8

이번 버전에서 체감이 가장 큰 변화다. 이제 `open()`에 `encoding`을 안 쓰면 **시스템 로캘과 상관없이 UTF-8**로 읽고 쓴다.

리눅스·맥은 원래 대부분 UTF-8이라 달라질 게 거의 없다. 문제는 **한국어 윈도우**다. 지금까지는 인코딩을 생략하면 로캘 인코딩(cp949)으로 열렸다. 그래서 이런 코드가 조용히 동작이 바뀐다.

```python
# 3.14까지: 한국어 윈도우에서 cp949로 읽음
# 3.15부터: UTF-8로 읽음 → 예전에 cp949로 저장한 파일이면 UnicodeDecodeError
with open("고객목록.csv") as f:
    ...
```

대응은 간단하다.

- **가장 좋은 방법**: 인코딩을 항상 적는다. `open(path, encoding="utf-8")`
- 정말 로캘 인코딩이 필요한 파일이면 `encoding="locale"` (3.10부터 지원)
- 당장 고칠 시간이 없으면 환경변수 `PYTHONUTF8=0` 또는 `python -X utf8=0`으로 예전처럼 돌릴 수 있다.

올리기 전에 3.14에서 `python -X warn_default_encoding 스크립트.py`로 한 번 돌려 보면, 인코딩을 생략한 곳마다 `EncodingWarning`이 떠서 고칠 곳을 바로 찾을 수 있다.

## 2. 지워진 것: 오래된 코드라면 확인

자주 걸릴 만한 것만 추렸다. 전체 목록은 공식 What's New의 Removed 항목에 있다.

| 지워진 것 | 대신 쓸 것 |
|---|---|
| `sre_compile`, `sre_constants`, `sre_parse` 모듈 | `re` |
| `http.server`의 `CGIHTTPRequestHandler`, `--cgi` 옵션 | 별도 WSGI/ASGI 서버 |
| `glob.glob0()`, `glob.glob1()` | `glob.glob(..., root_dir=...)` |
| `pathlib.PurePath.is_reserved()` | `os.path.isreserved()` |
| importlib 로더의 `load_module()` | `exec_module()` |
| `NamedTuple("P", x=int)` 키워드 문법 | 클래스 문법 |

그리고 `profile` 모듈은 이번에 deprecated, **3.17에서 제거 예정**이다. `cProfile`은 별칭으로 남는다.

## 3. 바로 써 볼 만한 것

### lazy import (PEP 810)

무거운 모듈을 실제로 쓸 때까지 불러오지 않는다. CLI 도구처럼 시작 속도가 중요한 코드에 좋다.

```python
lazy import json
lazy from pathlib import Path

print("시작")              # 아직 json, pathlib 안 불러옴
data = json.loads("{}")    # 여기서 json 로드
```

주의할 점은 셋이다.

- **모듈 최상위에서만** 쓸 수 있다. 함수·클래스 안, `try/except` 안에서 쓰면 SyntaxError다.
- import할 때 실행되는 부수 효과(설정 등록, 로그 등)에 기대는 코드는 시점이 달라진다.
- 3.14 이하도 지원해야 하면 키워드 대신 모듈 안에 `__lazy_modules__ = ["json"]`을 두는 방법이 있다. 일반 `import`가 3.15에서만 lazy로 동작한다.

[사진] `python -X importtime` 으로 lazy import 전후 시작 시간 비교 캡처

### frozendict (PEP 814)

내장 불변 딕셔너리다. 키·값이 모두 해시 가능하면 frozendict도 해시가 돼서 **dict 키, set 원소, `lru_cache` 인자**로 쓸 수 있다. 설정값이나 상수 테이블에 딱 맞다.

```python
DEFAULTS = frozendict(timeout=30, retries=3)
DEFAULTS["timeout"] = 10   # TypeError
```

`dict`의 하위 클래스가 **아니다**. 그래서 `isinstance(x, dict)`로 검사하던 코드는 frozendict를 못 받는다. `collections.abc.Mapping`으로 검사하자. 그리고 얕은 불변이라 값으로 넣은 리스트는 여전히 바뀐다.

### 컴프리헨션 언패킹 (PEP 798)

이중 for를 쓰던 평탄화가 한 줄로 짧아졌다.

```python
lists = [[1, 2], [3, 4], [5]]
[*L for L in lists]          # [1, 2, 3, 4, 5]
{**d for d in [{"a": 1}, {"b": 2}]}   # {'a': 1, 'b': 2}
```

### Tachyon 샘플링 프로파일러 (PEP 799)

새 `profiling.sampling` 패키지다. **실행 중인 프로세스에 PID로 붙어서** 코드 수정이나 재시작 없이 프로파일링할 수 있다. 플레임그래프·Firefox Profiler 형식 출력, top 같은 실시간 화면(`--live`)도 된다. 운영 중인 서버가 왜 느린지 볼 때 py-spy 대신 표준 도구로 해결할 수 있게 됐다.

## 4. 그 밖에 알아 둘 것

- **설치**: 윈도우는 새 Python 설치 관리자로 `py install 3.15` 한 줄이면 된다. 윈도우 64비트 공식 바이너리는 더 빠른 tail-calling 인터프리터로 빌드됐다.
- **free-threading**: 맥 공식 바이너리는 free-threading 빌드를 기본으로 함께 설치한다. free-threaded 빌드용 안정 ABI(abi3t)도 생겨서, C 확장 라이브러리들이 따라오기 쉬워졌다.
- **에러 메시지**: `[1, 2, 3].push(4)`에 `.append`를 제안하는 식으로 더 친절해졌다.

## 정리: 올려도 되나

| 상황 | 판단 |
|---|---|
| 새 프로젝트 | 바로 3.15로 시작해도 된다 |
| 기존 프로젝트 (리눅스·맥) | 제거된 API만 검색해 보고 올린다 |
| 기존 프로젝트 (윈도우) | `warn_default_encoding`으로 인코딩 생략 지점부터 고치고 올린다 |
| C 확장·과학 계산 라이브러리 의존 | 쓰는 라이브러리의 3.15 휠이 나왔는지 확인 후. 급하지 않으면 3.15.1까지 기다려도 된다 |

3.15는 화려한 기능보다 **"이제 인코딩은 UTF-8"이라는 기본값 정리**가 오래 남을 버전이다. 윈도우에서 파일 다루는 스크립트가 있다면 업그레이드 전에 `encoding=` 한 번씩 적어 두자.
