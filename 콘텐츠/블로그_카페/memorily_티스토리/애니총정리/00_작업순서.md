# 애니 총정리 글 쓰는 순서

나루토 글(2026-10-21)을 만든 과정을 다음 작품에도 그대로 쓰도록 정리한 것. 작품마다 이 순서를 따르고, 작품 md(01_나루토 …)에 진행을 적는다.

- 글 형식의 요약은 사이트별 템플릿 › memorily › 애니 카테고리 컨셉에도 있다 (2026-10-23, 변환 요청문에 들어간다). 이 md 를 고치면 컨셉도 같이 맞춘다.
- 애니 총정리 화면의 **글쓰기·변환** 버튼: 담은 작품 중 대기·작업 중인 것을 PC 터미널 claude 가 작품마다 새 터미널로 차례로, 이 순서대로 글쓰기부터 서버 넣기(발행예정글 + 매핑 + 변환 완료)까지 한다. 일일루틴과 따로 돈다 (apps/anime/run.py).

## 글 한 편의 모양

- 한 작품 = 한 글. 사이트 **memorily**, 카테고리 **애니**.
- 제목: `<작품> 회차정리 애니만화 환산기 명장면 등 모음` (사용자가 1등 글을 보고 정한 꼴)
- 순서: 화수 환산기 → 대표 그림 → (그 작품에서 가장 헷갈리는 것: 나루토·질풍전 이어 보기 / 블리치 TV→천년혈전·쿨 번호 / 헌터 1999 vs 2011 / 원피스 지금 어디까지) → 막대 그림 → 장별 대응 → 애니 오리지널 회차 → 자주 묻는 것 → 명장면 몇 화(사진) → 그 밖의 장면 표 → 출처·저작권. 작품마다 검색어를 보고 유연하게 (2026-10-21 사용자).
- 맨 위 요약은 넣지 않는다 (도구형 글). 정보를 '적어 두는' 느낌으로 짧게, 표 위주.
- 용어는 한국에서 부르는 이름 그대로 (나루토 때 '무인편'이라 썼다가 사용자가 처음 보는 말이라 했다). 일본 팬 말은 쓰지 않는다.
- '몇 기'로 찾는 작품(블리치)은 기 구분을 표로 적는다 (2026-10-21 사용자). 어느 기준(일본 DVD 시즌 · 라프텔 등)인지 밝힌다.
- 두 판이 있는 작품(헌터×헌터 1999·2011)은 왜 나뉘었는지 짧게 적는다 (2026-10-21 사용자).
- 극장판이 있거나 보는 순서가 있으면 '극장판' 표(개봉 · 보는 위치)를 명장면 앞에 둔다. 보는 위치는 공식이 아니라 흔히 안내되는 자리라고 밝히고, 안내가 엇갈리면 그렇게 적는다. 없으면 쓰지 않는다 (2026-10-21 사용자).

## 1. 수요 조사

- 구글 자동완성으로 실제 검색어를 모은다: `<작품> 몇`, `<작품> 몇화`, `<작품> 만화`, `<작품> 순서`, `<작품> 오리지널`, `<작품> 명장면`, 주요 인물 이름. (`suggestqueries.google.com/complete/search?client=firefox&hl=ko&q=…`, 파이썬 urllib 로 UTF-8)
- 자주 나오는 것: 몇 화 = 만화 몇 화·몇 권, 몇 화부터 이어 보나, 오리지널(필러) 건너뛰기, 보는 순서, 명장면 몇 화.

## 2. 회차 데이터 (가장 공들일 곳)

- 회차마다 `[만화 첫 화, 끝 화, 종류]`. 종류 1 원작 · 2 원작 + 애니 장면 · 0 애니 오리지널(만화 0).
- 출처 두 곳 이상 대조: 작품 fandom 위키 회차 문서(원작 화수) · Anime Filler List · Anime Filler Guide. 다르면 위키 화수를 따르고 다른 점을 작품 md 에 적는다.
- 권별 첫 화: 리디북스 등 한국판 권 목록 + 영어 위키백과 권 목록으로 대조.
- 명장면: 회차 제목으로 확인, 화수는 위 회차 데이터에서.
- 파일: `memorily_티스토리/애니환산기/data/<작품키>.json` — `{"name", "last", "vols": [권마다 첫 화], "series": [{"name", "eps": [...]}]}`. 시리즈가 나뉘면 series 를 여러 개로 (나루토 · 나루토 질풍전).
- 점검: 회차 수가 맞는지, 원작 화수가 거의 늘어나기만 하는지, 마지막 원작 화가 만화 끝 화와 맞는지.
- 연재 중인 작품은 `volEnd`(최신권 마지막 화)를 넣어 그 뒤 화가 '단행본 미수록'으로 나오게 한다. 번호가 음수인 화(블리치 과거편)는 `negvols` `[[처음, 끝, 권]]`.

## 3. 환산기

- 코드는 `memorily_티스토리/애니환산기/` (환산기.js · 글모양.css · build.py). data 에 작품 파일을 더하고 `python build.py` → `스킨에_붙일것.html` 이 새로 나온다.
- 사용자가 티스토리 스킨 HTML 의 `</body>` 위 환산기 부분을 새 파일로 바꿔 붙여야 새 작품이 뜬다 — 끝나고 꼭 알린다.
- 글 본문에는 `[환산기: <작품키>]` 한 줄 (한글 이름·onpiece 같은 오타도 받는다). 스킨 스크립트가 그 자리를 환산기로 바꾼다.
- 글모양(Pretendard·크기·굵기·간격·표)은 환산기 글만이 아니라 모든 글에 걸린다 — JB Office 글 관리 변환 화면과 같은 값 (2026-10-22).
  애니환산기/글모양.css 와 workspace/static/css/app.css 의 .st-flat 을 같이 고친다. 고친 뒤 build.py → 스킨에_붙일것.html 을 스킨에 다시 붙인다.
- 확인: 크롬 헤드리스나 playwright 에 calc.css·calc.js 를 넣어 애니→만화·만화→애니·오리지널 회차·범위 밖 숫자를 눌러 본다.

## 4. 원고와 서버

- 원고: `포스팅자동화/원고/T<번호>_<작품>환산기/원고.md` (사이트: memorily · 분류: 광고 수익 (조회수) > 콘텐츠·엔터).
- 서버에 넣기: `apps/writing/place_drafts.py` 의 `place(apps, "T85_블리치환산기")` 를 부르는 writing migration 을 원고와 같은 커밋에 넣는다 (0014 가 예). 발행예정글 + memorily › 애니 매핑 + 변환 완료.
- 작업은 처음부터 브랜치에서 (자동 동기화가 반쯤 된 파일을 main 에 올린다).

## 5. 사진

- 가공이미지: 대표(620×325, 작품 상징색 하나)와 '어디까지 만화 내용인지' 막대(회차 데이터로 그림). `애니환산기/사진/` 에 두고 raw.githubusercontent 주소로 붙인다.
- **표지는 쓰지 않는다** — 사용자가 나루토에서 모두 지웠다. 저작권이 출판사까지 퍼진다 (2026-10-21).
- 장면: 작품 fandom 위키의 장면 화면, **620 폭** (`/revision/latest/scale-to-width-down/620`, 블리치는 `&path-prefix=en` 필요). 명장면 5장 + 나머지는 표.
- 모든 그림은 620 폭 (사용자가 티스토리에서 620 으로 다시 붙였다). 가공이미지는 `python 그림.py <작품키> <색> "<한 줄>"` (애니환산기 폴더, 크롬 헤드리스).
- 끝에 저작권 한 줄: `사진: ⓒ 원작자 / 출판사 · 방송사 · 제작사, 표지 출판사`. 사용자가 책임지기로 했다 (2026-10-21).

## 6. 끝나고

- 작품 md 의 상태·글 주소·남은 일을 고친다.
- 스킨 파일이 바뀌었으면 사용자에게 다시 붙이라고 알린다.
